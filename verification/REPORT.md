# Verification of sampled claims

Second-pass agents re-checked 15 high-stakes claims from the library guides against primary sources on 2026-10-27. Each checker saw only the claim, not the original agent's sources or reasoning. 6 confirmed, 8 partly right, 1 wrong. Every correction was applied to the guides, and each guide records the check in `meta.reviewed`.

| # | Claim | Verdict | What changed | Source |
|---|---|---|---|---|
| A1 | GitHub changelog ~2026-08-14: OAuth Apps support expiring user tokens (8h) with refresh tokens (6 months), on by default for new OAuth Apps; up to 10 redirect URIs; per-URI wildcard/subpath redirect matching toggle. | **Confirmed** | No change needed. Small details to add: existing apps can opt in by requesting the offline_access scope or by forcing expiration app-wide. Turning it on does not expire tokens already issued. The 6-month refresh-token lifetime counts from last use. Apps that had a single callback URL before 2026-08-03 had wildcard matching turned on for that URL. Wildcard matching accepts subpaths, and the changelog also mentions subdomains, but the docs say the host must match exactly apart from subdomains. Check this subdomain detail before relying on it. | [official](https://github.blog/changelog/2026-08-14-multiple-redirect-uris-and-token-refresh-for-oauth-apps) |
| A2 | gmail.metadata is RESTRICTED; gmail.send is sensitive; gmail.labels is non-sensitive. | **Confirmed** | None | [official](https://developers.google.com/workspace/gmail/api/auth/scopes) |
| A3 | External app in Testing: refresh tokens expire 7 days after consent (unless only openid/email/profile), Testing limited to 100 test users. | **Confirmed** | No change needed. Optional: a test user counts against the 100-user quota as soon as they are added. Apps that request only the basic identity scopes do not need users on the test-user list. | [official](https://support.google.com/cloud/answer/15549945?hl=en ; https://developers.google.com/identity/protocols/oauth2) |
| A4 | Unverified production apps: lifetime cap of 100 new users that cannot be reset; Google's own page states CASA costs roughly $500-$4,500 per year. | **Partly right** | Google describes two different limits. (1) The Unverified apps page caps an app at '100 new users in total' until it is verified, says verification lifts the cap, and says quotas may be adjusted per app. (2) The separate 'user cap' on unapproved sensitive or restricted scopes is the one that lasts for the project's lifetime and cannot be reset. On cost: the $500-$4,500 range appears only on Google's Google Health API app-verification page, not on the general restricted-scope or Gmail pages. It is a fee per assessment, paid to the third-party assessor, and depends on the app's complexity. The assessment itself is required every year, but Google does not call the fee a yearly price. Suggested wording: 'about $500-$4,500 per assessment (Google Health API docs), and the assessment must be repeated every year.' | [official](https://support.google.com/cloud/answer/15549945?hl=en ; https://support.google.com/cloud/answer/7454865 ; https://developers.google.com/health/app-verification ; https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) |
| A5 | Since 29 May 2025, new installs of commercially distributed non-Marketplace apps limited to 1 req/min and max 15 objects on conversations.history/replies; did pre-May-2025 installs become subject on 3 March 2026? | **Partly right** | The limit itself is confirmed: from 2025-05-29 it covers new unlisted apps and new installs of existing unlisted apps, and drops conversations.history and conversations.replies from Tier 3 to Tier 1 (1 request per minute, limit default and maximum of 15). Apps built by a customer for internal use are exempt and keep Tier 3 (50+ per minute, up to 1,000 objects). Whether older installs became subject on 3 March 2026 cannot be settled from Slack's pages. The current changelog entry on docs.slack.dev, which the old api.slack.com FAQ URL now redirects to, says existing installs 'will not be impacted' and gives no date. Slack's legacy api.slack.com changelog index pages still say the limits apply to existing installs 'on March 3, 2026'. I found no Slack post confirming the limit was actually enforced on older installs. The guide should present this as unresolved, citing both pages, and tell readers to test against a real older install. The conversations.history reference page still lists only Tier 3. | [official](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps ; https://api.slack.com/changelog/deprecations) |
| A6 | Since ~July 2026 an app needs at least 10 active workspace installs before Marketplace submission; review: up to 10 business days preliminary, up to 10 weeks functional. | **Confirmed** | Confirmed. Add: 'active' means used in the past 28 days, and sandboxes do not count. The app must stay at 10 or more installs for the whole review. The guidelines also reject apps with fewer than 10 weekly active users. Functional review takes up to 10 weeks for new submissions and up to 6 weeks for published apps resubmitting changes. A resubmission after preliminary feedback restarts the queue. The 10-install rule raised the threshold again from the 5 installs that applied from August 2025. | [official](https://docs.slack.dev/changelog/2026/09/01/slack-marketplace-install-requirement ; https://docs.slack.dev/slack-marketplace/slack-marketplace-review-guide) |
| A7 | Marketplace rejects apps whose only function is an MCP server with no meaningful in-Slack functionality; AI apps may not store Slack data and may not use it to train LLMs. | **Partly right** | The MCP rule and the ban on training LLMs on Slack data apply as stated: the training ban appears both in the list of unsuitable apps and in the generative-AI rules. The no-storage rule is narrower than the claim. It sits under 'Agent or Assistant UI' and reads 'DON'T store any Slack data you obtain. Store metadata instead ... i.e. zero-copy'. The general generative-AI section does not ban storage. Instead it asks the developer to disclose retention, data tenancy and data residency. Suggested wording: apps using the Agent/Assistant UI must not store Slack data (zero-copy, metadata only), and every AI app must disclose how long it keeps data. Requests for *:history and similar scopes also trigger an enhanced review. | [official](https://docs.slack.dev/slack-marketplace/slack-marketplace-app-guidelines-and-requirements) |
| B1 | Microsoft-managed default user consent policy (rolled out mid-2025, default for new tenants) blocks user consent to Mail.Read/ReadWrite, Calendars.*, MailboxSettings.*, Contacts.ReadWrite for multi-tenant apps; admin consent required; no publisher-verified exemption. | **Partly right** | The permission list and 'no verified-publisher exemption' are right, and it is the default for new tenants. Fix the timeline: the mid-2025 rollout only blocked Files.Read(Write).All and Sites.Read(Write).All. Mail, calendar, mailbox and Teams scopes were added around Nov 2025, and more (Contacts/Tasks/People-type) were added in 2026. The Learn page lists Mail.*, Calendars.*, MailBoxSettings.*, Contacts.ReadWrite, Contacts.*.Shared, Tasks.*, People.Read and EAS/EWS/IMAP/POP. It does not list Contacts.Read or Mail.Send. The rule covers every app on a user-consent request, not only multi-tenant ones, and only in tenants still on 'Let Microsoft manage your consent settings'. The one exemption is a separate Microsoft policy for named mail clients (Apple Mail, Spark, eM Client, Thunderbird, etc.). Point users at the admin consent workflow. | [official](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies) |
| B2 | Publisher verification requires a vetted Microsoft AI Cloud Partner Program (ex-MPN) account; publisher domain must match a verified domain; verification is free. | **Confirmed** | Add some precision. The Partner One ID must be the partner global account (PGA); a location ID will not work. The email domain used in CPP verification must match the app's publisher domain or be a DNS-verified custom domain in the tenant, and *.onmicrosoft.com does not qualify. The app's tenant must be associated with the PGA and the app registered with a work/school account. The user needs App Admin or Cloud App Admin plus CPP Partner Admin or Account Admin, and MFA. | [official](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview) |
| B3 | As of Spring '26 new Connected App creation is disabled by default; ECAs replace them; a local ECA works only in its own org, so reaching customer orgs needs a packaged ECA in a 2GP managed package installed by each customer. | **Partly right** | The Spring '26 block is right. Local ECAs cannot be distributed; set Distribution State = Packaged and ship the ECA in a 2GP managed package. One nuance: the global OAuth settings (consumer key/secret) are not packaged and stay in the dev-hub/owner org. Do not frame per-customer install as a pure ECA artifact. It is also what the Sept 2025 'uninstalled app' restriction (B4) requires for non-admin users, so customers must install the package either way. | [official](https://developer.salesforce.com/docs/atlas.en-us.sfdx_dev.meta/sfdx_dev/sfdx_dev_auth_connected_app.htm ; https://trailhead.salesforce.com/content/learn/modules/external-client-app-basics/package-and-distribute-external-client-apps) |
| B4 | Since ~Sept 2025 users cannot authorize connected apps not installed in their org unless they hold 'Approve Uninstalled Connected Apps' / 'Use Any API Client'. | **Partly right** | The restriction is right: enforcement ran from about Sep 2 to Sep 17, 2025 for existing orgs, and from Aug 28/Sep 1 for new orgs. | B8 | Notion docs disagree on whether a public integration's Authorization URL exists before 'submitted for review'; does Notion now rotate refresh tokens (change ~June 2026)? | **Partly right** | Authorization URL: the current Authorization guide is the authoritative text and says the field populates only after the public connection is submitted for review, in the Configuration tab. The Public connections guide only says to find it in the Configuration tab and does not contradict this; older wording ('once made public') is superseded. Marketplace listing is a separate security review. Refresh: the refresh endpoint returns a new access_token and a new refresh_token. The docs do not say whether the old refresh token is invalidated, so store the new one each time. The June 8, 2026 changelog entry is a different change: new public connections mint a fresh access/refresh pair on every successful OAuth authorization (including re-auth), where they previously returned the existing active token.
